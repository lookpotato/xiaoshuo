# 旧系统提供的养料

这份记录只解释 V2 为什么这样设计，不会自动进入写稿上下文。

## 已确认的问题

- 旧入口要求一次读取 23 个文件、约 6.9 万字配置，还未计入最近章节正文。
- 同一上下文同时承担设定理解、人物模拟、正文生成、对白修正、图片规划、读者验收、归档和发布准备。
- 同一要求重复出现在管理器任务、session、作品 automation_prompt、共享规则、style_guide 和质量门槛中；措辞略有差异时没有明确裁决者。
- 机器验收主要确认文件、字段、哈希和引用存在。大量章节通过门槛仍不能证明陌生读者看得懂，也不能证明语言具有作者辨识度。
- 每次遇到新问题就增加禁令，逐渐使写作变成同时躲避多类错误，模型容易生成解释充分但生活感薄弱的平均文本。

## V2 对应决策

- 作者模块位于作品和章节之上；未校准偏好必须保持未知。
- 导演、作者、陌生读者使用独立上下文，审稿规则不进入初稿生成。
- 写作阶段最多两个模块，其中章节因果固定占一个位置；只允许一个最相关的专项模块进入。
- 读者阶段只把理解断裂判为阻塞，文风建议和偏好差异只能记录。
- 发布、图片和 Git 从创作上下文移出，由后续适配器处理。
- 旧提示词不直接迁移。只有能对应真实失败样本、具有适用边界并经过作者确认的经验，才能进入作者配置或模块库。
